# 生成搭配

从 `data/library.json` 构建一整套本地搭配集合：选出优质组合、为每套生成方形模特图、逐张校验，并把成品清单与图片存到 `data/` 下。

## 先问数量

除非用户已给出明确数量，否则先问 `你想要生成几套搭配？`。不要静默使用默认值。

当用户给出季节、场合、着装要求或风格方向时一并获取；否则在不过度追问的前提下，做一组均衡的日常搭配。

拿到数量后要端到端做完，不要只给出建议、清单或提示词就停下。

## 要求

- 生成图片前先阅读并遵循内置的 `imagegen` 技能。
- 需要 `data/library.json`、足够的上下装、以及本地身份参考图 `data/model-reference.png` 或 `WARDROBE_MODEL_REFERENCE`。
- 所有源衣物与身份图只存本地、保持不变。
- 绝不把 `data/`、身份参考图、衣物图或生成图加入 Git。
- 只使用当前数据库中存在、且本地资源可解析的衣橱单品。
- 生成的数量必须与请求数量一致，每套恰好一张通过审核的模特图。

## 并行

用户要求超过 8 套或明确要求并行时使用子代理。始终由主代理负责完整衣橱盘点、全局组合唯一性、单品使用均衡、清单汇总与最终 QA。

给每个 worker 不相交的搭配 ID，以及精确的身份图与衣物参考图路径，并要求其返回搭配 ID、填好的提示词、参考图列表、生成路径、状态与视觉复核记录。绝不允许两个 worker 生成或写入同一个搭配 ID。并发受限时按波次推进，每波后汇总结算，只重跑缺失或失败的 ID。

## 1. 盘点衣橱

读取 `data/library.json`，把 `/api/import/library/FILENAME` 资源解析到 `data/imported/FILENAME`。按以下品类分组：

- `upperbody` — 上装
- `wholebody_up` — 外套与外层
- `lowerbody` — 下装
- `accessories_up` — 可选配饰
- `shoes` — 可选鞋履

每个记录含中文字段 `name`、`subtype`（中文细分品类）与 `season`（spring/summer/autumn/winter）。挑选时结合元数据与视觉证据，不要只看文件名或颜色。

抽查最多 12 件抠图的棋盘格拼版并逐一检查。若衣橱无法支撑请求数量的真正差异化搭配，告知用户最大可用数量并询问是否按该数量继续。

## 2. 策划组合

每套必须恰好一件上装与一件下装，可选一件外套、鞋履与克制的配饰。遵循以下原则：

- 优先同色系或邻近色，保证整体协调。
- 补色对比要克制，并保持单一主色或主单品。
- 让一件图案、肌理或高饱和单品承担视觉重点。
- 平衡视觉重量与廓形：下装较满时上装更干净；重外套压在简洁内搭上。
- 用外层来框住内搭、呼应已有颜色，或加入一次受控对比。
- 叠穿要物理合理，且每件所选单品都要清晰可辨。
- 分散单品使用，别总依赖最容易的中性款。

若用户指定了季节或场合，据此覆盖有用场景；无明确方向时，在衣橱允许范围内均衡休闲、通勤/半正式、暖季、叠穿、深色调与个性造型。季节匹配时优先选用 `season` 覆盖当季的单品。

构建 `$WORK/outfits.json`，达到最终目标数量：

```json
{
  "version": 1,
  "outfits": [
    {
      "id": "navy-camel-classic",
      "name": "藏青与驼色经典",
      "occasion": ["通勤", "半正式"],
      "garmentIds": ["import-...", "import-..."],
      "reason": "深藏青与驼色形成受控的冷暖对比。",
      "setting": "安静的暖石色庭院，点缀克制的绿植",
      "image": "outfit-images/navy-camel-classic.png",
      "status": "planned"
    }
  ]
}
```

搭配 ID 用小写连字符保持稳定。即使名称或场景不同，也要拒绝重复的衣物组合。

## 3. 准备参考图与提示词

为每套搭配创建一个生成包：

1. 身份参考图
2. 精确的上装抠图
3. 精确的下装抠图
4. 可选：精确的外层抠图
5. 仅在刻意选择时：精确的鞋履或配饰

阅读 [references/outfit-image-prompt.md](references/outfit-image-prompt.md)，按该搭配记录填入模板。选择叠穿子句前先检查每张外层参考图，绝不要臆断拉链、纽扣、门襟、开口或闭合方式。

在整组中轮换克制的暖色自然场景，同时保持统一的编辑风格。

## 4. 生成每套搭配

用 Imagegen 为每套生成一张 1:1 方形模特 PNG。通过审核前，工作产物放在 `data/` 之外。每次调用只传最小的有效参考集，但绝不遗漏任何所选单品。

集合较大时分批生成。把每套标记为 `planned`、`generated`、`accepted` 或 `failed`，只重跑缺失或失败的 ID。

## 5. 校验与修正

逐张对照身份图与全部衣物参考。抽查最多 12 套的拼版，再逐张打开存疑图片。

必须满足：

- 可辨识的身份、脸、发型、年龄、体型与身体比例
- 每件所选单品都在场且可辨认
- 衣物颜色、材质、版型、结构、图案、logo、文字、比例与闭合方式精确
- 从头到脚的完整取景，搭配可读、人体解剖真实
- 叠穿自然，没有臆造的开口或隐藏内搭
- 没有未选的可见衣物，除非未选鞋时允许的素色中性鞋或隐形基础层
- 无第二个人、文字叠加、水印、商品图风格或合成 AI 塑料感

身份漂移、缺失或被改款的衣物、虚假闭合或文字、人体结构错误或脚部被裁切，都要重生成。不得仅凭「看起来合理」就标记通过。

## 6. 本地交付

全部搭配通过后：

1. 按需创建 `data/outfit-images/`。
2. 把每张通过的 PNG 复制到 `data/outfit-images/OUTFIT-ID.png`。
3. 仅当应用暴露该端点时，把清单 image 设为 `/api/import/outfits/OUTFIT-ID.png`；否则保留仓库相对路径 `outfit-images/OUTFIT-ID.png`。
4. 原子写入精确的请求集合到 `data/outfits.json`。
5. 重新打开每个复制文件，校验图片数量、唯一搭配 ID、通过审核的清单记录数均等于用户请求数量。

除非应用确实有搭配路由，不要声称当前画廊会展示搭配。成品本地资源与清单本身就是交付物。

## 完成

报告请求数量与完成数量、输出路径、任何重生成过的失败项与风格配比。在对话中最多展示 12 套模特图，并指向本地文件夹说明其余部分。
